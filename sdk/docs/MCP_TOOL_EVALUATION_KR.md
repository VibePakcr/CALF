# MCP 도구 계약과 평가

CALF는 기존 작업에 맞는 도구인지, 해당 호출을 CALF 경로에서 실행해도 되는지, 결과가 별도로 정한 조건을 충족하는지 확인합니다. MCP 서버를 만드는 기능이나 에이전트에 새 권한을 주는 기능은 아닙니다.

대상 버전은 **하네스 1.8.12·Workbench 1.9.8**입니다. 실검증 범위는 macOS ARM64·Windows x64·Linux x64(Debian 13)에서 검토·고정한 **로컬 stdio 읽기, 호스트 실행 경로를 거친 새 후보 생성, 미리 설정한 로컬 복구**입니다. 전체 프로그램은 `FOUNDATION_READY`이며, `INTEGRATION_VERIFIED`는 첨부 증거에 명시한 로컬 경로에만 적용합니다. 이 결과를 임의의 제공자·통신 방식·운영체제에 확대해 적용하지 않습니다. 기존 배포판·설치된 호스트·기록·설정도 자동으로 바뀌지 않습니다.

## 구분해서 보는 네 가지 판정

| 판정 | 상태 | 의미 |
| --- | --- | --- |
| 계약 검사 | `VALID`, `INVALID`, `INCOMPLETE`, `UNVERIFIED`, `INCOMPATIBLE` | 형식과 지원 스키마·프로토콜을 확인합니다. `VALID`는 실행 권한이나 안전성 인증이 아닙니다. |
| 도구 선택 | `SUITABLE`, `UNSUITABLE`, `AMBIGUOUS`, `INSUFFICIENT_CONTEXT` | 작업에 필요한 기능과 로컬 정책에서 별도로 검토한 기능을 비교합니다. 작업 목표를 바꾸지 않습니다. |
| 호출 검사 | `ALLOW`, `DENY`, `REQUIRE_APPROVAL`, `REQUIRE_REVALIDATION` | `tools/call` 직전에 작업·정책·서버·도구 신원, 인수, 정확한 대상, 선택한 레인과 부작용 분류를 확인합니다. |
| 결과 검사 | `RESULT_VALID`, `RESULT_INVALID`, `RESULT_INCOMPLETE`, `RESULT_UNVERIFIED` | 응답 수신, 출력 형식, 로컬 파일 근거, 기대값과 프로세스 종료를 나누어 확인합니다. 도구의 `success=true`만으로는 부족합니다. |

도구 이름·설명·annotation·자료·오류·결과 텍스트는 신뢰할 수 없는 데이터입니다. `readOnlyHint`, 응답에 담긴 지시, 요청의 `approved` 값으로 권한을 얻을 수 없습니다. 기존 호스트와 운영체제의 승인·권한 경계도 그대로 적용됩니다.

## 로컬 정책 준비

먼저 **기존 네이티브 TASK가 수락된 작업**을 선택합니다. 기존 scope와 검사 기준은 고치지 않습니다. 정책은 작업 폴더·태스크 ID·TASK 봉투의 정확한 해시를 서버와 도구 규칙에 연결합니다.

1. 기존 권한 안에서 서버 실행 파일과 소스, 시작 시 발생할 수 있는 동작을 검토합니다. 도구 탐색도 해당 프로세스를 시작하므로, 탐색 자체가 읽기 전용이거나 안전하다고 가정하면 안 됩니다.
2. `tool-contract`의 `pin-server` 동작으로 기존 CALF 실행 파일 고정 검사를 사용합니다. `adapter`에는 기존 런타임 명세의 `schema`, `id`, `role`, `command`, `files`, `capabilities`, `class`를 넣습니다. 이 단계는 파일을 해시할 뿐 실행하지 않습니다.
3. 확인한 도구 목록을 `normalize`로 정규화합니다. 입력은 `server: {id, protocolVersion}`과 `tools`입니다. 반환된 이름·스키마·지문을 검토합니다. 검토한 기능은 로컬 규칙에 기록하며, 도구의 설명에서 권한을 추론하지 않습니다.
4. `calf.mcp.policy.v1` 정책 파일을 만들고 파일 바이트 전체의 해시를 구합니다. 정책이 바뀌면 새 해시를 명시해야 합니다. 서버가 알리는 도구 계약이 달라진 경우에도 별도 재검증이 필요합니다.

정책에는 다음 항목이 들어갑니다.

| 항목 | 내용 |
| --- | --- |
| `workspace`, `task`, `taskHash` | 실제 작업 폴더와 기존 수락 TASK의 정확한 봉투 해시. |
| `server` | `{id, adapter}`. `adapter`는 네이티브 고정 검사로 받은 명세·파일 신원입니다. 절대 경로 명령과 실행 파일·스크립트 신원을 다시 확인합니다. |
| `requiredCapability` | 해당 작업에 필요한 기능. 서버의 지시문에서 추론하지 않습니다. |
| `rules` | 정확한 도구별 규칙. 최대 32개입니다. |
| `timeoutMs` | 연결·요청 경로에 적용할 100~5000ms 한도. 소유 프로세스 정리 시간이 별도로 있으며 자동 재시도하지 않습니다. |
| `gcn` | `null`, 또는 같은 작업 폴더에 대해 선택한 레인·모듈을 확인하는 기존 `guard` 요청. 범위 확인은 검사 통과나 실행 허가가 아닙니다. |

규칙은 `name`, `fingerprint`, `capabilities`, `effect`, `enabled`, `paths`, `postconditions`, `resultChecks`로 구성합니다. 부작용 분류는 `read`, `write`, `delete`, `external`, `unknown`입니다. 검토한 읽기 작업은 직접 호출할 수 있습니다. 쓰기는 정확한 실행안을 준비한 뒤 기존 호스트 실행 경로를 거쳐야 하며, 현재는 새 후보 생성만 지원합니다. 기존 파일 덮어쓰기와 삭제·외부 전송·미확인 부작용은 실행할 수 없습니다.

경로 규칙은 `{pointer, allowed}` 형태로, 입력의 JSON 포인터와 TASK scope에 이미 있는 정확한 상대 파일명을 연결합니다. 부모 경로 이동, 임의 절대 경로, 심볼릭 링크·하드링크 대상은 거부합니다. 파일 사후조건은 scope 안의 `{path, sha256}`이며 하나 이상 필요합니다.

결과 검사도 하나 이상 필요합니다. `{kind:"equals", pointer, value}`로 기대값을 비교하거나, `{kind:"file-sha256", pointer, path}`로 반환값을 CALF가 직접 읽은 파일 해시와 대조합니다. 읽기 작업에서는 전체 scope의 전후 스냅샷도 같아야 합니다. 후보 생성은 대상 파일이 실행 전에 없어야 하고 정확한 사후조건이 필요합니다. GCN 계획을 사용하면 선택한 모듈에 쓰기 소유권도 있어야 합니다. 다른 scope 파일은 그대로 유지돼야 합니다. 대상은 최대 4개, 파일당 4MiB로 제한합니다. 이 검사가 임의의 의미적 품질이나 scope 밖의 모든 변화를 검증하는 것은 아닙니다.

쓰기 규칙에 `recovery:"local-artifact-and-native-checks"`를 **실행 전에** 넣으면 응답을 잃은 경우 별도 호스트 실행으로 로컬 후보를 검증할 수 있습니다. 원래 응답이 유효해졌다는 뜻은 아닙니다. 생략하거나 `"none"`으로 설정하면 불명확한 호출을 확정하지 않습니다. 복구에는 원래 정책 해시가 필요하므로 실패 후 옵션을 추가해 과거 실행을 승인할 수 없습니다.

## 명시적으로 호출하기

```sh
calf tool-contract < normalize-request.json
calf tool-call /absolute/policy.json EXACT_POLICY_SHA256 < request.json
```

호출 요청 예시는 다음과 같습니다. 실제 작업의 정책과 파일명으로 바꿔 사용합니다.

```json
{"action":"invoke","name":"read_asset","arguments":{"path":"notes.txt"},"requestId":"read-notes-1"}
```

그 밖의 동작은 `discover`, `status`, `reconcile`입니다. 탐색은 고정한 서버를 시작했다가 닫고, 상태 조회는 기존 네이티브 완료 판정을 읽습니다. `reconcile`은 안전 정지 점검과 현재 스냅샷을 기록합니다. 재전송하거나 미종결 호출을 지우거나 파일을 복원하거나 성공을 추정하지 않습니다.

필요하면 포그라운드 MCP 연결도 사용할 수 있습니다.

```sh
calf tool-mcp /absolute/policy.json EXACT_POLICY_SHA256
calf tool-mcp /absolute/policy.json EXACT_POLICY_SHA256 --control
```

기본 도구는 `calf_tool_status`뿐입니다. `--control`을 명시하면 고정한 정책 안에서 읽기용 `calf_tool_invoke`와 실행안 준비용 `calf_tool_prepare`를 제공합니다. 이 옵션이 사용자 승인이나 운영체제 권한을 새로 만들어 주지는 않습니다. 등록·정책 수정·승인 생성은 MCP 도구로 노출하지 않습니다. 입력이 닫히면 포그라운드 연결도 종료되며 상주 프로세스를 남기지 않습니다. 호스트 설정도 자동으로 쓰지 않습니다.

## 호스트 실행을 거쳐 후보 생성하기

`calf_tool_prepare`에 `{request: {...}}`를 보내면 정확한 실행안과 로컬 관리 기록을 만들고 `REQUIRE_APPROVAL`, 검토 요약, 실행 명령을 반환합니다. 요청한 도구는 실행하지 않습니다. CLI로는 다음과 같이 준비합니다.

```sh
calf tool-prepare /absolute/policy.json EXACT_POLICY_SHA256 < write-request.json
```

요청에는 앞의 `invoke` 형식을 사용합니다. 반환된 작업 버전·정책·도구 지문, 인수·대상, 등록 검사와 만료 시각을 검토한 뒤 `argv`를 **기존 호스트 승인 절차**로 실행합니다. 명령은 `calf execute TICKET TICKET_SHA256` 형태입니다. 내부 전달용 명령을 직접 호출해 쓰기를 실행할 수는 없습니다.

기존 네이티브 실행 진입점이 티켓을 검증하고 한 번만 소비합니다. 실행안은 코어·정책·요청·대상과 scope의 파일 버전·작업 버전·만료 시각에 묶입니다. 그 사이 인수·정책·코어·검토 파일이 달라지면 실행을 거부합니다. 기본 유효 시간은 120초이며 CLI에서는 100ms~300초로 지정할 수 있습니다. 실제 전달 전에 만료를 확인하며 몰래 연장하지 않습니다.

**이 기록은 정확한 명령이 호스트 실행 경로를 거쳤다는 근거이며, 사용자가 승인 버튼을 눌렀다는 독립적인 서명 증명은 아닙니다.** 실행 허용 여부는 기존 호스트 정책이 결정합니다. CALF가 영구 허용 규칙·자격증명·전역 권한·별도 승인 엔진을 추가하지 않습니다. 도구의 annotation이나 요청의 승인 표시도 사용자 동의로 취급하지 않습니다.

정상 후보 생성 후에는 등록된 네이티브 검사를 모두 자동 실행해 현재 완료 판정을 확인합니다. 유효한 도구 응답이나 종료 코드 0만으로는 완료하지 않습니다. 이 경로에서는 기존 승인본을 쓰기 대상으로 삼을 수 없습니다. 후보 채택은 별도의 Work 계약 동작입니다.

## 기록·완료·복구

탐색, 계약 검사, 선택, 호출, 결과, 안전 정지 판단은 기존 작업의 **`history.html` 해시 체인에 collector ACTION으로 추가**합니다. 별도의 이벤트 DB를 만들지 않습니다. 요약에는 정책·도구·인수·결과 해시를 연결하며, 신뢰할 수 없는 응답 텍스트를 복사하지 않습니다. 원래 응답은 요청한 클라이언트에 데이터로 반환합니다.

실행 추적에는 기존 네이티브 `begin`/`finish`를 사용합니다. 도구와 프로세스 종료를 관측한 ACTION은 통과 CHECK가 아닙니다. 읽기 작업도 등록된 독립 검사가 필요하고, 후보 생성은 그 검사를 자동 실행합니다. 결과가 잘못됐거나 불완전하거나 정리가 불명확하면 시작 기록은 미종결로 남고, 이후 다른 파일 검사에 통과해도 기존 완료 엔진은 `UNKNOWN`을 유지합니다. 실제 검사 실패는 `VIOLATED`로 남습니다.

검증한 후보에는 작업 버전과 정확한 scope 스냅샷을 묶는 필수 **`mcpArtifact` ACTION 계약**이 붙습니다. 약한 검사 명령이 종료 코드 0을 반환해도 파일이 달라지면 완료로 인정하지 않습니다. 이 계약을 모르는 구버전 코어는 기록을 무시하지 않고 거부해 `UNKNOWN`을 반환합니다. `calf --version`의 기능 목록에서 `mcp-host-intent-v1`, `mcp-artifact-v1` 지원 여부를 확인할 수 있습니다. 기존 기록은 변환하거나 다시 쓰지 않습니다.

같은 논리 요청 ID는 정책이나 서버 별칭이 바뀌어도 두 번 실행하지 않습니다. 미종결 호출이 있으면 새 ID를 붙여 재전송하는 것도 막습니다. 시간 초과·연결 단절의 최초 기록을 보존합니다. 기존 `reconcile`은 여전히 상태 점검만 수행합니다.

원래 쓰기 정책에 로컬 복구를 미리 설정했다면 다음 요청을 별도로 준비합니다.

```json
{"action":"settle","sourceTicket":"/absolute/original-ticket.json","sourceTicketHash":"EXACT_ORIGINAL_TICKET_SHA256"}
```

`calf_tool_prepare` 또는 `tool-prepare`로 준비·검토한 뒤 같은 호스트 실행 절차를 거칩니다. 원래 기록된 실행안, 보존한 런타임, 정확한 네이티브 종료 영수증과 소유 프로세스 그룹의 종료 확인이 필요합니다. 새 실행안에 해당 영수증과 현재 scope를 고정하고, 후보의 기대 해시·보호 파일 보존·새로 실행한 등록 검사를 확인합니다. `tools/call`을 다시 보내지 않습니다. 원래 영수증·오류·결과 분류·기록은 그대로 두고 조정 결과와 CHECK를 추가합니다.

영수증이 없거나 달라졌거나 다른 작업의 것이면 확정하지 않습니다. 계약·산출물 변경, 불명확한 프로세스 정리, 명시적 취소도 복구를 막습니다. 취소한 실행안은 종결된 것으로 취급합니다. 응답 대기와 독립 검사에서도 인터럽트뿐 아니라 기존 네이티브 취소 마커와 호스트 실행권 유지 신호를 확인합니다. 별도의 감시 서비스는 추가하지 않습니다. 외부 제공자의 작업은 별도의 신뢰할 수 있는 조회·취소 계약이 필요합니다. 로컬 파일 복구만으로 원격 작업 종료나 이미 발생한 비용의 환급을 보장할 수는 없습니다.

## 현재 지원 범위

- MCP `2025-11-25` JSON-lines stdio이며, 정책 하나에 명시적으로 고정한 로컬 서버 하나를 연결합니다. 페이지가 남은 도구 목록, 중복 키·식별자, 프로토콜 차이, 도구 목록 변경은 통과시키지 않습니다.
- 스키마는 boolean, 기본 `type`, 객체 속성·필수값·추가 속성, 배열 항목·길이, 문자열 길이·정규식, 숫자 범위, `enum`, `const`를 제한적으로 지원합니다. 최상위 입력·출력은 객체여야 합니다. 알 수 없는 키워드, `$ref`, `format`, 타입 합집합과 미지원 방언은 `UNVERIFIED`입니다. 외부 참조를 내려받지 않습니다. 숫자 비교 범위는 유한한 ±(2^53−1)입니다.
- 도구 64개, 규칙 32개, 스키마 12단계·512개 노드, 호출 인수 2KiB와 기존 네이티브 기록 한도를 적용합니다. CPU로 요청할 때만 처리하며 상주 캐시·로컬 모델·워커 풀은 없습니다.
- 서버를 고정해 실행해도 그 서버의 파일시스템·네트워크 접근을 운영체제 수준에서 제한하는 것은 아닙니다. CALF는 이 경로의 인수와 선택한 상태를 검사합니다. 별도로 실행한 호출, 일시적인 부작용, scope 밖의 변경까지 통제한다고 보장하지 않습니다.
- 이 소스에는 GCI·외부 ETS 정본이 확인되지 않았습니다. 소유자가 확인한 현재 GCN/MCL과 네이티브 기록 경계를 유지합니다. 일반 삭제·외부 전송, 원격 작업 복구, Repository 모듈 자동 연결과 다른 OS·통신 방식 지원은 후속 과제입니다.

## SDK에서 사용하기

SDK 0.2.5는 Python의 `tool_contract`, `tool_status`, `prepare_tool`, `tool_mcp_server`와 Node의 `toolMcpServer`를 제공합니다. 연결 명세를 반환했다고 호스트에 등록된 것은 아니며, 실행안을 준비했다고 실행 권한을 얻는 것도 아닙니다. [SDK 안내](../README_KR.md)와 `examples/mcp_policy.py` 예제를 참고하세요. 네이티브 정책과 요청은 UTF-8로 저장하고, 정책 파일의 정확한 바이트와 소문자 SHA-256을 함께 확인합니다.

Windows 복구 시험은 요청 한도 1500ms, Unix 시험은 400ms를 사용했습니다. 최초 Windows 400ms 시험은 전달 전에 만료돼 호출 0회·후보 없음·UNKNOWN으로 끝났으며 별도로 보존합니다. 복구 검증에는 실제 쓰기가 일어난 뒤 응답이 시간 초과된 결과를 사용했습니다. 완료 기준이나 후보의 기대 해시는 낮추지 않았습니다.
